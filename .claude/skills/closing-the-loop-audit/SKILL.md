# 收尾审计：揪出高速开发积累的半成品债务

## 这个 skill 解决什么

速度本身不会让代码质量整体下降。真正的代价是：**"功能接了一半就停"的比例会系统性
升高**——因为生成/编写一个功能的速度，远超"验证这个功能真的端到端连通"的速度。人
（尤其是被 AI 辅助放大产出速度之后）会不自觉地用"写完了多少"替代"验证过多少"作为
进度的感觉。

这在独立开发 + AI 辅助编码的组合下尤其严重，因为：
- AI 生成代码的那次对话里，往往没有运行环境去验证"这段代码真的被接线调用了吗"；
- 独立开发没有 code review 这道天然关卡，装配错误不会被另一双眼睛拦下来；
- 高速迭代下，"看起来对"和"跑起来对"之间的检验被系统性跳过。

结果是一类特定的债务：**业务逻辑本身往往没错，错在"它有没有被真正接通"**。这个 skill
就是教你怎么系统性地把这类债务挖出来。

## 核心判断：功能"写完"和"连通"是两件事，前者不能替代后者

问自己："如果我现在真的调一次这个功能，它会通到底吗？"——不是看代码逻辑对不对，是
看**装配**对不对：依赖真的被注入了吗？路由没被别的路由屏蔽吗？失败分支真的会被
下游正确解读吗？没被触发过的代码路径，其正确性是未知数，不是默认成立。

## 排查方法：五类"半成品"信号，配对应的排查手段

### 1. 装配缺口——依赖占位符从未被真正注入

许多框架的依赖注入用"占位符 + 运行时覆盖"模式（FastAPI 的 `Depends()` +
`dependency_overrides`、Spring 的 `@Autowired`、任何"接口先定义、实现后接入"的模式）。
写占位符的那一刻和真正接线的那一刻是两个不同的动作，中间很容易漏掉后者——占位符
本身如果写得"响亮"（抛异常而不是返回空），至少调用时会报错；但如果没人真的调用过
一次，这个缺口可以存在很久没人发现。

**排查手段**：列出所有"声明了依赖占位符"的地方，逐一确认对应的"运行时覆盖/装配"
代码是否存在且被执行到。不要只读装配代码本身有没有写对，要读**装配代码是否覆盖了
全部声明过的占位符**——这是一个需要两边对照数数量的检查，不是读一遍代码就能看出来的。

*本项目实例*：RAG 服务的 `crag._runner_dep` 与 `structured._client_dep` 两个依赖占位符，
从服务写出来到审计发现，从未出现在 `main.py` 的 `dependency_overrides` 里——对应的
四个端点全部一调就 500，因为没人真的调用过它们。

### 2. 路由/接线冲突——同一入口注册了两次，后一个屏蔽前一个

功能模块各自开发时容易忽略"这个路径是不是已经被别的模块占了"。这类冲突不会在
开发时报错（框架允许注册但只有最先匹配的生效），只有真正调用到被屏蔽的那个路径
时才会发现"怎么调的是另一个模块的逻辑"。

**排查手段**：列出所有路由注册（endpoint path + method），检查是否有重复/包含关系；
检查注册顺序是否让后一个永远拿不到请求。

*本项目实例*：`crag.py` 的 `APIRouter()` 没设 prefix，与 `query.py` 同样注册了
`POST /query`；`query.py` 先注册，`crag` 端点即便修好了依赖注入也永远调不到。

### 3. 反思/回环逻辑两端都写了，但路由/触发从没接上

复杂一点的功能（重试逻辑、状态机的条件分支、审核-修正循环）常常是"两端各自完整，
中间的连接线没画"——评审组件输出了判定字段，修正组件也准备好读取评审意见重新生成，
但编排层的路由代码里那根线从未连上，两个组件各自"看起来完整"掩盖了它们从未真正
协作过的事实。

**排查手段**：对每一个"应该有回环/条件分支"的编排点，直接读路由/状态转移的代码，
确认条件判断真的存在且指向了正确的目标，而不是想当然地认为"两端都写了，中间肯定
连上了"。

*本项目实例*：SQL 迁移的 critic（评审）组件早就会输出 `needs_correction`，patcher
（修正）组件也早就会读取上一轮评审意见重新生成，但编排图里 critic 到 reporter 是
无条件边——回环逻辑的两端都写完了，路由代码里从来没有把它们接起来。

### 4. 失败路径只测过"能编译"，没测过"触发时下游会不会被骗"

高速开发时人会本能地先让成功路径跑起来，然后就转向下一个功能——失败分支"写了
try/except"就算完工，没人真去触发一次异常，看看它到底报的是什么。这类债务最阴险，
因为它不影响 demo，只在真正出故障时才现形，而现形的方式是"谎报成功"而不是报错。

**排查手段**：找到所有 `catch`/`except` 块和所有"服务不可用时降级"的分支，逐一
问："这个分支被触发时，它返回/设置的值，下游会不会把它当成成功？"——如果答案是
会，这就是需要修的静默失败（诊断修复的具体方法见 diagnosing-silent-failures skill）。

*本项目实例*：SQL 迁移的 critic LLM 调用失败时，异常处理分支曾经写的是
`"STATUS: CORRECT"`——"评审没跑成"被谎报成"评审通过"。任务状态机遇到某一步 FAIL
后仍然无条件上报 `status: completed`。这两处 catch 块都"能编译、不崩溃"，掩盖了
它们在说谎的事实。

### 5. 决策类代码（指标、实验、评分逻辑）从未验证过是否真的在测量它自称测量的东西

被当成"一次性工具"写的评测/实验代码尤其容易在这里出问题：写完跑一次拿到数字就
算完工，没人验证过这批数字是否真的有区分度、是否真的只受你要观察的那个变量影响。

**排查手段**：对任何会被用来做决策的数字，先问"如果我手造两个我知道答案的输入，
这段代码能分辨出来吗"——如果没试过，这个数字目前只是"看起来像结论"，不是结论。

*本项目实例*：消融实验的 Recall@5 在 84 个 case 里有 74 个在不同检索模式间完全
相同——这个指标对这批数据早就饱和了，没人在下结论前验证过它是否还有区分度。

## 系统性扫一遍的具体做法

不要指望"记得住去检查"，用可重复的动作代替记忆：

1. **搜索自我标注的"没做完"标记**：`TODO`、`FIXME`、`NotImplementedError`、
   `unimplemented`、`raise NotImplementedError` 之类。这些是开发者自己承认的缺口，
   最容易找也最常被遗忘。
2. **搜索"吞异常"模式**：`except Exception: pass`、catch 后返回默认值/空结果、
   降级但不留痕的分支。每一个都要问第 4 类信号里那句话。
3. **列出全部路由注册，检查前缀/路径冲突**：不要只看某一个文件，要把整个项目的
   路由表拼起来看。
4. **列出所有"依赖占位符声明"，对照实际的装配/注册代码，数量对不上就是缺口**。
5. **手动调用一遍你记不清是否测过的端点/功能**——如果连"记不记得测过"都不确定，
   基本可以假设没测过。
6. **对决策类代码，补至少两个"已知答案"的边界断言**，验证它的判别力，而不是只信
   它能跑出一个数字。

## 怎么预防（不是靠自觉，是靠改变工作方式）

- **重新定义"完成"**：一个功能只有同时满足"业务逻辑写完"和"装配验证过、失败路径
  测过"才算完成，前者不能替代后者。写完立刻手动触发一次调用，比事后靠记忆去检查
  可靠得多。
- **把"收尾"和"开发"分成两种不同的工作模式**：开发时的心流是"做完 A 就想做 B"，
  收尾需要的是完全相反的注意力——怀疑自己刚写的东西、专门找茬。物理上把这两种
  时段分开：固定安排"零新功能，只验证已有功能是否真的连通"的时段，就是在做本
  skill 描述的这套排查。
- **让系统自己在缺口处喊出来，而不是指望人记得检查**：占位符用"抛异常"而不是
  "返回空/None"；降级路径显式打标志（`*_real`、`degraded`）而不是静默继续；这样
  即使收尾检查漏掉了，系统运行时也会自己暴露问题——这是 diagnosing-silent-failures
  skill 教的具体修复手法，本 skill 负责先把这些暗角找出来。
- **定期做"考古式"审查，而不是只在出问题时才查**：不要等用户报 bug 才排查，主动
  假设半成品广泛存在，用上面六条动作系统性扫一遍，而不是随手翻几个文件找感觉。

## 和 diagnosing-silent-failures 的关系

本 skill 负责**主动找**：在没人报告具体问题的情况下，系统性扫描一个高速迭代的
项目，揪出装配缺口、路由冲突、失败路径谎报、指标未验证这几类典型半成品债务。
diagnosing-silent-failures 负责**深挖修**：一旦怀疑或发现了某个具体的"能跑通但
结果不对"的现象，怎么定位根因、怎么把静默失败改造成响亮失败。实践中往往是先用
本 skill 扫出一批可疑点，再对每一点用 diagnosing-silent-failures 的四步法逐个
诊断修复。
