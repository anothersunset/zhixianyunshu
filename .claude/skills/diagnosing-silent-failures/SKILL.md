# 诊断静默失败（Silent Failures）

## 这个 skill 解决什么

最难查的 bug 不是崩溃——崩溃会给你栈。最难查的是**系统在骗你**：它照常运行、返回
看似合理的结果，但结果是错的，而且没有任何红色报错。典型症状：

- 测试时好时坏，重跑有时又过了
- 消融 / AB 实验做完，梯度不单调、甚至和预期相反（本该更好的配置反而更差）
- 改了代码，指标纹丝不动
- 流水线 / 状态机报"成功""completed"，但产物明显不对
- 文件在编辑器里看着是正常代码，实际是乱码 / 编码损坏

这些表面上是不同的 bug，内核是**同一个**：某处的失败被静默吞掉了——降级成了低质
量路径、混入了污染数据、或者干脆谎报了成功。查这类问题，靠的不是更用力地读某一个
函数，而是一套"**先不信绿灯**"的诊断纪律。

## 核心心法：先不信"绿灯"

普通 debug 从报错出发。静默失败没有报错，所以第一步是**反转默认信任**：当一个结果
"能跑通但我不信"时，把"它成功了"本身当作待验证的假设，而不是已知前提。

问自己三个问题，几乎能定位所有静默失败：

1. **它是真的成功了，还是只是"跑完了"？** ——"返回了结果"不等于"返回了正确结果"。
   服务返回了文档，但可能是 hash 伪向量算出来的垃圾；任务报了 completed，但某一站
   其实 FAIL 了只是没人上报。

2. **每一档 / 每一次，实验条件真的一样吗？** ——只有当"除了你要观察的那个变量，其余
   全部相同"时，对比才有意义。部分样本走了降级路径、部分走了真实路径，混在一张表里，
   梯度就是噪声。

3. **失败发生时，它会喊出来吗？** ——沿着数据流每一跳问："这里如果出错 / 组件不可用，
   会 fail loud 抛出来，还是 fail silent 降级继续？"静默降级点就是 bug 的藏身处。

## 诊断四步法

### 第 1 步：从真实产物量化，别从理论猜

不要一上来读代码猜原因。**先看它实际产出了什么**——日志、结果 JSON、报告文件、指标
表。用数据确认"哪里不对、错得有多系统"，再去代码里找为什么。

> 本项目实例：消融"梯度递减"的问题，是先读 `eval/results/ablation_report.md` 的实测
> 数据，看到 Vector 组低于 BM25、大量 case 的 Recall@5 **完全相同**——这个"完全相同"
> 是决定性线索，说明各档根本没产生差异——才反推到代码。若一开始就扎进检索代码，会
> 淹没在细节里。

**关键动作**：找到能量化问题的那个产物；找到那个"不该出现却出现"的规律（全都相同、
全都为 0、单调性被打破、某个字段恒定）。那个规律往往直接指向根因类别。

### 第 2 步：把"那一个变量"端到端追一遍

静默失败常发生在**参数传导链的某一跳被无声地丢弃或改写**。选定你以为在起作用的那个
变量，从入口一路跟到最底层，每一跳都确认它真的被传下去、被用上了。

> 本项目实例：把检索模式 `mode`/`retrieval` 从 `run_eval.py` → `MigrationClient` →
> `MigrationEvalController` → RAG `retriever.search` 逐跳追。要确认的不只是"参数有没有
> 传到"，还有"传到之后有没有真的改变行为"——`use_dense = mode in (...)` 这类分支如果
> 上游 embedder 已降级，参数传对了也没用。

**关键动作**：对每一跳问两件事——参数到了吗？到了之后**真的改变行为了吗**？后者更容易
被忽略。

### 第 3 步：把"跑了"和"在正确条件下跑了"分开

这是静默失败的核心。一个组件可以"在线"（有响应）却"降级"（响应是垃圾）。你需要一个
**能力探针**去区分"它回话了"和"它在用真实实现回话"。

> 本项目实例：`Embedder` 在 BGE-M3 不可用时降级为 SHA-256 hash 伪向量，`Reranker`
> 不可用时静默 noop——`/retrieve` 照常返回结果，但 vector/rerank/full 各档实为同一个
> 噪声通道。光测"有没有返回"永远发现不了，必须读服务上报的 `capabilities`，确认
> `dense`/`rerank` 是真实模型在线。

**关键动作**：找到系统里所有"不可用时降级而非报错"的点（搜 `fallback`、`degrade`、
`mock`、`try/except` 里 `pass` 或返回空、`if x is None: x = <占位>`）。每一个都是一个
需要显式探针去照亮的暗角。

### 第 4 步：确认失败语义——失败时状态如实吗

流程 / 状态机类的静默失败，问题在**失败发生了但状态没如实反映**。中间某步失败，整体
却报成功。

> 本项目实例：`AgentRunner` 遇节点异常会 break 停止执行，但 `TaskExecutionService`
> 原先无条件 `trace.finish(status=completed)`——失败任务在 Langfuse 里显示成功。修复
> 是引入 `failed` 标志，按 step 的真实 FAIL 状态上报 `failed`。

**关键动作**：找到"汇报最终状态"的那行代码，逆着问：如果中途失败了，这行会不会照样
报成功？成功路径和失败路径是不是共用了同一个收尾？

## 修复模式：让静默变响亮

诊断清楚后，修复的总原则只有一句：**把静默失败改造成响亮失败**。四个可复用模式：

### 模式 A — Fail Loud 守卫
让降级 / 失败**显式抛出或显式标记**，而不是默默继续。调用方要么感知到并主动处理，
要么直接中止。
- 例：RAG `/retrieve` 异常时抛 `HTTPException(500)` 而非返回空 `items`——空结果会被
  下游误当成"检索无命中"，而不是"检索挂了"。
- 例：后端 meta 透出 `retrieval_real` 布尔；`MigrationClient` 见到 `False` 直接中止
  实验（除非显式 `ALLOW_MOCK_RETRIEVAL=1`），避免污染样本混入。

### 模式 B — 条件探针（Preflight）
在跑昂贵流程 / 采信结果之前，**主动探测每一个"必须为真"的前提**，任一不满足就红灯。
- 例：`preflight.py` 读 `capabilities`，`dense`/`rerank`/`graphrag` 任一降级即 fail，
  除非 `--allow-degraded`（仅冒烟用途）。
- 心法：实验 / 流程的可信度不在"跑了多少"，而在"每一档条件是否真的只差你要观察的那
  个变量"。前提没探针，结论都可能是假的。

### 模式 C — 有区分度的指标
如果指标"不动"，先怀疑**指标本身饱和**了，而不是改动无效。换一个能分辨你所关心差异的
指标。
- 例：文档池小时各模式 top-k **集合**相同，集合型 `Recall@5` 全饱和；而 rerank/CRAG
  改变的是**排序**不是集合。换排序敏感的 `MRR@10`（命中排第 1 位=1.0、第 5 位=0.2），
  梯度立刻显形。
- 心法：指标要匹配你想观察的那个维度。测排序就别用集合指标；测尾部就别只看均值。

### 模式 D — 运行时兜底守卫
对循环 / 状态机 / 递归，加**步数上限**和**非法状态守卫**，防止配置错误导致无声的死循环
或崩溃。
- 例：`AgentRunner` 加 `MAX_STEPS=32` 全局兜底（反思回环无出口时不至于无限跑），路由
  到未注册节点时以可读 FAIL 终止而非 NPE。
- 心法：守卫不是为了正常路径，是为了"配置写错了"这种你现在还没想到的未来。

### 修复损坏文件的特例：恢复 + 重放，绝不手改
遇到编码损坏 / 乱码 / 被工具批量搞坏的文件，**不要试图手工修复乱码**——那是不可逆的猜
测。正确策略：从版本库 `git show HEAD:<path>` 恢复干净版本，再把其中真正有价值的实质
改动用干净编码**重新应用一遍**。区分"损坏"和"改动"，只保留后者。
- 例：本次 10 个文件被 GBK 误读 UTF-8 重写并加 BOM，其中夹带着有价值的改动。策略是先
  逐个 `git diff` 确认哪些是损坏、哪些是真改动，恢复后只重放真改动。

## 下次如何避免（预防清单）

静默失败的根子在"**默认信任 + 默认降级**"的编码习惯。写系统时反过来：

- **降级必须留痕**：任何 `fallback` / `mock` / 占位路径，都要在返回值 / 响应 meta 里带一
  个显式标志（`*_real`、`degraded`、`source`），让调用方能判断这次是不是真的。
- **能力要可自省**：服务暴露 `capabilities` / `health` 端点，如实报告每个子组件是真实
  在线还是降级占位。别让"进程活着"被误当成"功能正常"。
- **实验前先 preflight**：昂贵实验 / 评测跑之前，先跑一遍前提探针，条件不满足直接拒绝
  开跑，别等跑完几小时才发现数据是脏的。
- **指标带自检**：汇总里显式统计"污染样本数""系统错误数"，并给出排除污染后的口径，让
  失真在报表上一眼可见，而不是被平均值抹平。
- **状态机 fail loud**：失败路径和成功路径分开收尾；中途失败绝不能走到"报成功"的那行。
  加步数上限和非法状态守卫。
- **CI 挡住已知的坑**：把踩过的静默坑变成自动检查——比如 BOM / 乱码检测、`git grep`
  常见乱码高频字，作为 pre-commit / CI gate，让同类问题下次在提交前就红灯。

## 一句话总结

> 静默失败的通用解法是：**先不信绿灯，从真实产物量化异常，端到端追那一个变量，把"跑了"
> 和"在正确条件下跑了"分开，然后把每一个静默降级点改造成响亮的失败。**

## 和 closing-the-loop-audit 的关系

本 skill 是**深挖修**：已经怀疑或发现了某个具体的"能跑通但结果不对"的现象，怎么
定位根因、怎么改造成响亮失败。如果还没有具体线索、只是想系统性排查一个高速迭代/
AI 辅助开发的项目里有没有装配缺口、路由冲突、回环没接上等半成品债务，先用
closing-the-loop-audit skill 做**主动找**，扫出可疑点后再回来用本 skill 逐个诊断。
